# Наблюдения HLS и сохранение трека — 29.10.2026

**Уточнение v0.2.4:** сохранённые исходники подтвердили дополнительную обработку ключевого ответа в ветке `X-Encrypted-Key`, а также возможность встроенного master. Поэтому код обычного raw identity-key downloader и 16-байтный ответ из HAR не подтверждают работу этого режима сервиса. См. [разбор исходников](zvuk-source-findings.md).

## Что сообщил реальный пользовательский отчёт

Первичная диагностика наблюдала на `cdn-hls-slicer.zvuk.com` четыре `.m3u8` с MIME `application/vnd.apple.mpegurl`, семь `.m4s` и два `.mp4` с MIME `audio/mp4`. Счётчики отражали доступную историю Performance API и не доказывали принадлежность всех ресурсов одной песне. `audio/mp4` описывает контейнер; `.mp4` в HLS может быть init-фрагментом.

В расширенном структурном отчёте master объявляет:

| Вариант | Объявленный CODECS | Объявленный BANDWIDTH, бит/с |
| --- | --- | ---: |
| HE-AAC v2 | `mp4a.40.29` | 64 780 |
| AAC-LC | `mp4a.40.2` | 129 451 |
| AAC-LC | `mp4a.40.2` | 257 479 |
| FLAC | `fLaC` | 945 387 |

Два исследованных media-плейлиста описаны как VOD: каждый содержит 21 сегмент и один `EXT-X-MAP`, объявленные длительности — 189,682 и 189,729 секунды. Зафиксированы `AES-128` с `KEYFORMAT=identity`; byte ranges и discontinuity в этих плейлистах не наблюдались.

`matchesCurrentTrackIdInPath: true` означает совпадение однозначного DOM ID композиции с числовым компонентом пути ресурса. Это полезная привязка, но история по-прежнему может включать несколько вариантов одной композиции. Инспектор сохраняет `currentPlaylistAssociation: unconfirmed` и metadata на момент наблюдения; downloader дополнительно требует единственный прочитанный master.

**FLAC здесь объявлен master-плейлистом. Настоящий FLAC-поток пользователя не декодирован и не прослушан этой проверкой.** BANDWIDTH — декларация потока, а не измеренная характеристика декодированного аудио; битовая глубина, sample rate и подтверждённая lossless-передача из этого отчёта не следуют.

В первичном отчёте было `media: []`: обычный DOM-поиск не обнаружил `audio`/`video`. Причина не установлена. Поэтому отсутствие найденных `mediaKeys`/событий `encrypted` не доказывает отсутствие DRM. Структурный отчёт позволяет поддержать обычный AES-128 identity, но не даёт общего заключения обо всех вариантах сервиса.

## Что реализовано в расширении

1. MAIN reader с `document_start` пассивно наблюдает Resource Timing и хранит только в памяти до 32 публичных адресов `.m3u8` точного `https://cdn-hls-slicer.zvuk.com`.
2. После явного нажатия «Скачать песню» проверяются свежие metadata, DOM ID и ключ текущего документа. Кандидаты сопоставляются по ID с границами цифр; рассматривается до восьми адресов.
3. Сервис читает кандидаты и требует единственный настоящий master. При нескольких master, отсутствии подтверждённого ID или источника выводится причина; первый media-плейлист или последний запрос не выбираются произвольно.
4. По умолчанию берётся поддержанный AAC-вариант с наибольшим объявленным BANDWIDTH; FLAC рассматривается при отсутствии AAC. В данном отчёте таким AAC-кандидатом является объявленный AAC-LC с BANDWIDTH 257 479.
5. Для конечного VOD fMP4 читаются init и упорядоченные сегменты. При AES-128 identity читается только указанный плейлистом 16-байтный ключ разрешённого CDN либо подтверждённого маршрута `https://zvuk.com/keyserver/api/v1/key`. Для второго варианта разрешены ровно три публичных параметра: числовой `track_id`, `quality=hq|lossless`, `content_type=track`; ID сверяется с выбранной композицией до запроса ключей/аудио. URI не угадывается и не переписывается. Web Crypto выполняет CBC-дешифрование обычного HLS; ключ импортируется неэкспортируемым, исходные байты очищаются.
6. Проверяются ISO BMFF-структура, аудио-entry init и соответствие выбранному AAC/FLAC. Init и фрагменты соединяются по порядку в Blob `audio/mp4`; временный Blob URL готового файла передаётся background для `chrome.downloads.download`.

Результат HLS-сохранения — **фрагментированный MP4 с расширением `.m4a`**. FLAC-вариант также остаётся в этом контейнере: сырой `.flac` и MP3 не создаются. Аудио не перекодируется; структурная проверка не заменяет декодирование и оценку качества настоящего файла.

Ключи, сетевые URI и содержимое плейлистов не сохраняются в Chrome Storage и не публикуются в логах/сообщениях background. URL готового page-owned Blob используется для сохранения и освобождается после завершения/прерывания, отмены или замены канала; запоздавший результат отменённого задания тоже освобождается. Резервный TTL — пять минут, одновременно удерживается один готовый файл.

## Пределы поддержанного потока

* Плейлисты/init/сегменты — только точный HTTPS CDN, без query, fragment, credentials и явно заданных портов. Для ключа также разрешён объявленный плейлистом точный маршрут Звука с тремя публичными параметрами, перечисленными выше. С v0.2.5 браузер может использовать обычную авторизацию страницы на этом маршруте через `credentials: same-origin`. Для CDN задано `credentials: omit`. Все запросы используют `redirect: error` и `referrerPolicy: no-referrer`. Расширение не читает cookies и не добавляет служебные заголовки авторизации.
* До 64 MiB суммарно, 8 MiB на ресурс, 256 KiB текста плейлиста и 16 ключей. Читаются не более двух ресурсов одновременно, между началами запросов проходит не меньше 300 мс. Очередь общая для повторных попыток внутри одной страницы; разные вкладки имеют отдельные очереди. Таймаут ресурса — 15 секунд после начала запроса; подготовка ограничена 150 секундами, включая ожидание очереди. Автоматических повторов нет.
* Конечный VOD: до 1000 сегментов и 1800 секунд, один поддержанный init. Live, byte ranges, discontinuity и другие неподдержанные структуры отклоняются.
* `SAMPLE-AES`, CENC, EME/DRM-сигналы, неподдержанный KEYFORMAT и URL лицензий/DRM отклоняются. Получение DRM-лицензий, извлечение CDM-ключей и обход ограничений не реализованы.
* Heartbeat раз в пять секунд работает только во время задания. Уход со страницы, потеря фонового задания и таймаут отменяют подготовку; повторное действие создаёт новое задание.

## Что проверено, а что осталось проверить

Подтверждены TypeScript, production-сборка/Manifest и 193 автоматических теста в 31 наборе (30.10.2026, v0.2.3). Unit-проверки покрывают master/media parsing, AES-128/IV, структуру MP4, порядок сегментов, выбор AAC, строгие URL, очистку ключей, отмену, ограничения памяти, интервалы запросов, восстановление статуса загрузки, безопасный HLS-discovery и точный маршрут identity-ключа с проверкой ID.

В настоящем Chrome полный путь проверен на **собственном AAC-fixture**: подготовка зашифрованных тестовых init/сегментов, сборка M4A, сохранение через реальный Chrome Downloads API и сравнение байтов с исходным файлом размером около 13 KB. Chrome воспроизвёл полученный M4A до `ended`.

Отдельный браузерный сценарий подтвердил отмену активной подготовки после принудительной остановки worker и успешный повтор сохранения. Обычный прямой MP4 не блокируется прошлой историей HLS другого трека: переход в HLS применяется при кандидатах текущего DOM ID.

**Скачивание настоящей песни в авторизованной пользовательской сессии Звука этим сценарием не проверено.** Реальный отчёт подтверждает структуру конкретных плейлистов и объявления master; собственный fixture подтверждает работу реализации на контролируемых байтах. Доступность всех ресурсов в реальной сессии и фактический звук сохранённой песни требуют ручной проверки.

После новой сборки обновите расширение **и перезагрузите вкладку Звука**, сверьте номер в заголовке Popup с актуальным `package.json`, затем включите трек и дождитесь определения его ID. Нажмите «Скачать песню», проверьте диалог и сохранённый `.m4a`, прослушайте начало и конец. Если источник неоднозначен, закрыт CORS, использует параметры доступа или неподдержанное шифрование, операция должна завершиться понятной причиной. Последняя попытка сохраняется после закрытия popup; кнопка «Копировать диагностику» копирует публичные текстовые metadata и код состояния без сетевых URL и данных авторизации. Включённая аудиодиагностика добавляет признаки ресурсов и счётчики `hlsDiscovery`, которые помогают отличить пропущенное наблюдение от исключённого адреса.

Предоставленный скрипт виджета подтверждает заполнение Media Session и выявил отдельную проблему сравнения списка исполнителей, исправленную в v0.2.0. Он импортирует внешний движок и не содержит достаточной информации для восстановления логики сервера ключей. Подробнее — [разбор виджета](zvuk-widget-findings.md).

Предоставленный позднее HAR подтвердил имя папки `/drm/` как причину отклонения источников и позволил проверить точный маршрут стандартного identity-ключа. В v0.2.3 три реальных плейлиста разобраны локально без чтения ключей/аудио и воспроизведения запросов. В Chrome проверен собственный fixture с той же формой пути и key URI, без cookies/Authorization. Подробнее — [проверка HAR](zvuk-har-findings.md).

Дополнительные Console-скрипты остаются доступны, но не обязательны для обычного сохранения. `collect-zvuk-diagnostics.js` наблюдает Web APIs без запросов; `inspect-zvuk-hls.js` v2 в течение 15 секунд ловит новые плейлисты и выдаёт структурный отчёт, не запрашивая сегменты/init/ключи. У v1 возникал `candidateCount: 0` из-за отсутствия подходящей записи в одном снимке истории; v2 отдельно учитывает live discovery и причины фильтрации. Точную причину прежнего пустого снимка без таких данных установить нельзя.

## Основание интерпретации

[RFC 8216](https://www.rfc-editor.org/rfc/rfc8216.html): разделы 3.3 (fragmented MP4), 4.3.2.4 (EXT-X-KEY), 4.3.2.5 (EXT-X-MAP), 4.3.4.2 (EXT-X-STREAM-INF), 5.1–5.2 (ключ и IV). Эти правила описывают HLS; конкретные форматы/доступность сервиса подтверждаются его наблюдаемыми данными, а не самим стандартом.
