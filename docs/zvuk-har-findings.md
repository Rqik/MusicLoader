# Проверка предоставленного HAR — 30.10.2026, v0.2.3

**Уточнение после анализа сохранённой сборки (v0.2.4):** в запросе HAR присутствует `X-Encrypted-Key`, а плеер преобразует ответ перед использованием. HTTP 200 и 16 байт не доказывают, что это уже raw AES-key. Код v0.2.3 поддерживает обычный raw identity-key сценарий; специальная обработка ключевого ответа сайта не реализована. Подробнее — [разбор исходников](zvuk-source-findings.md).

Журнал исследован локально как данные. Запросы из него не воспроизводились, содержимое ключевых и аудиоответов не извлекалось, исходный HAR в проект не копировался. Заголовки авторизации, cookies, полные URL и значения служебных параметров в отчёт не включены.

## Причина отказа поиска источника

В журнале есть master и два media-плейлиста с успешными ответами. Все используют unsigned HTTPS-адреса разрешённого CDN и папку `/drm/`. Проверка `resolveHlsUrl` считала это имя достаточным признаком неподдерживаемой защиты и отклоняла адреса ещё до разбора HLS. Отсюда `acceptedObservations: 0`, `storedPlaylists: 0`, `rejectedOther > 0`.

Имя каталога больше не определяет метод защиты. Сохраняются проверки тегов, KEYFORMAT, EME, SAMPLE-AES/CENC, ISO BMFF и обращений к лицензиям.

## Подтверждённая структура

- Master объявляет четыре варианта: три AAC и один FLAC. Это объявления, а не проверка качества декодированного аудио.
- Оба media-плейлиста — конечный VOD с init и 18 сегментами; заявленная длительность около 158,6 секунды.
- Метод — `AES-128`, KEYFORMAT отсутствует, что означает `identity`; IV указан явно.
- Ключ указан по точному маршруту `https://zvuk.com/keyserver/api/v1/key` с публичными `track_id`, `quality` и `content_type=track`. Наблюдавшиеся значения качества — `hq` и `lossless`. Метаданные одного ответа указывают HTTP 200, `application/octet-stream`, 16 байт; тело ключа не исследовалось.
- Числовой ID в key URI совпадает с ID пути соответствующего media-плейлиста. HAR и отдельно присланный снимок Popup относятся к разным ID: они не объединяются в доказательство текущей композиции.

Все три HLS-текста успешно разобраны обновлённым парсером локально. Для получения ключа добавлена только указанная схема: ровно три неповторяющихся параметра, соответствие текущему Track ID, без подстановки credentials, Authorization, подписи или изменения URL. Ошибка доступа останавливает загрузку без автоматического повтора. Ключ остаётся в MAIN-памяти и очищается по существующим правилам.

По [RFC 8216, разделам 4.3.2.4 и 5](https://www.rfc-editor.org/rfc/rfc8216.html#section-4.3.2.4), отсутствие KEYFORMAT означает identity, а его AES-128 key file состоит из 16 бинарных байт. Это основание для поддержки стандартной схемы HLS; название папки не заменяет проверку протокола. Отсутствие DRM во всех режимах сервиса этим не установлено.

Сохранение настоящей песни в авторизованной сессии пользователя пока не подтверждено. Проверка полного пути выполнена в Chrome 156 на собственном AAC-fixture с той же формой CDN-пути и маршрута ключа: запрос без cookies/Authorization при установленной тестовой cookie, один ключ на задание, сохранение M4A, сравнение байтов и воспроизведение до `ended`. Все 193 автоматических теста, TypeScript и production-сборка проходят. Настоящие ключи и аудио из журнала не используются.

В новом HAR от 12.11.2026 видны шесть ответов `.m4s` и один `.mp4` с MIME `audio/mp4` и HTTP 200. Журнал охватывает получение фрагментов. Отдельный отчёт MusicLoader 0.2.7 показывает HTTP 400 при чтении ключа на 15%. Эти данные подтверждают сегментированную доставку, а полный незашифрованный источник для трека не подтверждён.
