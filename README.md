# MusicLoader

Расширение Google Chrome Manifest V3 показывает метаданные текущего трека веб-плеера [Звука](https://zvuk.com/), сохраняет их по вкладкам и обновляет popup при переключении композиции. Реальное состояние плеера отделено от демонстрационной очереди.

Стек: React, TypeScript strict, Rsbuild, Sass/SCSS, Tailwind CSS, оригинальные shadcn/ui-компоненты, Zustand и Lucide React. По нажатию кнопки расширение сохраняет прямой аудиофайл или собирает поддерживаемый HLS VOD в M4A через Chrome Downloads. Аудио не перекодируется; DRM, SAMPLE-AES и лицензионные механизмы не поддерживаются.

При запросе ключа к проверенному маршруту Звука расширение генерирует восьмизначное одноразовое значение `X-Encrypted-Key` по схеме найденного плеера. Успешный ответ этого маршрута отмечается кодом `hls-wrapped-key`. Обработка ключа в формате плеера ещё требует доработки. Для записи воспроизводимого звука доступен отдельный режим WebM/Opus. [Подробный разбор исходников](docs/zvuk-source-findings.md) описывает эту ветку, встроенный master-плейлист и обложки.

## Запуск и установка

Нужны Node.js **22.18+**, npm и Chrome **120+**.

```sh
npm ci
npm run typecheck
npm test
npm run build
```

`npm ci` устанавливает версии из `package-lock.json`. Для обновления зависимостей используйте `npm install` и сохраняйте обновлённый lockfile.

1. Откройте `chrome://extensions` и включите «Режим разработчика».
2. Нажмите «Загрузить распакованное расширение» и выберите **папку `dist`**.
3. После обновления расширения нажмите на его карточке «Обновить» и **перезагрузите уже открытую вкладку Звука**: это загружает новые content scripts.
4. Откройте MusicLoader и сверьте версию под названием расширения с `package.json`. После перезагрузки запустите композицию на Звуке. Метаданные должны появиться после ближайшей проверки, обычно примерно через секунду.
5. Когда карточка покажет текущий трек, нажмите **«Скачать песню»** и дождитесь подготовки файла и диалога Chrome. Для HLS требуется подтверждённый ID. Диагностический отчёт для нажатия кнопки больше не требуется.

При обновлении добавляется необходимое разрешение `downloads`. Подтвердите его в интерфейсе Chrome, если браузер приостановил расширение до принятия нового разрешения.

Если после нажатия файла нет, снова откройте popup. Этап и причина последней попытки сохраняются. Чтобы получить короткий отчёт с версией, состоянием связи и кодом ошибки, раскройте **«Дополнительные действия»** и нажмите **«Копировать диагностику»**. Кнопка **«Открыть загрузки»** доступна после получения идентификатора загрузки Chrome.

Если получено `no-source` при `progress: 0` и `downloadId: null`, этап получения источника не пройден и скачивание через Chrome ещё не запускалось. Наблюдение MP4/M4S-сегментов в диагностике не подтверждает наличие доступного master-плейлиста. Сначала обновите расширение и вкладку Звука, затем запустите трек. Если проблема остаётся, раскройте «Дополнительные действия», включите «Диагностику аудио», дождитесь отчёта и нажмите «Копировать диагностику».

В версии 0.2.2 исправлено отбрасывание HLS-master в начале большого пакета Resource Timing: прежняя проверка последних 500 записей могла пропустить плейлист перед множеством ресурсов. Отчёт копирования версии 2 включает включённую аудиодиагностику и `hlsDiscovery`: режим наблюдения, ограниченные счётчики замеченных/сохранённых/подходящих текущему ID плейлистов и причины исключения (параметры доступа, другой CDN, другие ограничения). Это счётчики обработанных наблюдений, включая возможный повтор истории; они не являются числом уникальных сетевых запросов и не подтверждают принадлежность всех ресурсов текущему треку. URL, пути, значения query, cookies и заголовки в них отсутствуют. Старый формат аудиодиагностики поддерживается.

Наличие плейлистов с неподдерживаемыми параметрами доступа больше не маскируется общей ошибкой отсутствия источника. Если сайт не раскрывает плейлист в Performance API страницы, например запрос выполняется в другом контексте, браузерных наблюдений может быть недостаточно. Проверка настоящей авторизованной сессии не выполнялась; отдельная подтверждённая HAR причина отклонения плейлистов исправлена ниже.

В v0.2.3 предоставленный HAR позволил установить причину `rejectedOther`: unsigned-плейлисты отклонялись из-за имени папки `/drm/`. Само имя каталога больше не считается определением метода защиты; методы и формат ключа проверяются по тегам HLS и структуре media. HAR подтвердил master и два конечных AES-128 identity media-плейлиста по 18 сегментов, а также точный маршрут identity-ключа. Все три плейлиста успешно разобраны обновлённым парсером локально, без сетевых запросов и извлечения ключей или аудио из HAR. Детали — в [проверке HAR](docs/zvuk-har-findings.md).

## Повышение версии после каждого изменения

После каждого законченного логического изменения версия повышается один раз. Правило для следующих правок закреплено в `AGENTS.md`.

| Команда | Изменение версии | Когда использовать |
| --- | --- | --- |
| `npm run version:patch` | `0.2.0 → 0.2.1` | Исправление или небольшая правка |
| `npm run version:minor` | `0.2.1 → 0.3.0` | Новая функциональность |
| `npm run version:major` | `0.3.1 → 1.0.0` | Несовместимое крупное изменение |
| `npm run version:check` | Без изменения | Проверка согласованности |

Команды обновляют `package.json`, обе корневые версии в `package-lock.json` и `public/manifest.json`. Popup и предпросмотр получают актуальную версию без ручного изменения исходников. Git-коммиты, теги и публикация не выполняются.

Перед итоговой сборкой выполните нужное повышение, затем `npm run build`. Сборка проверяет версии и останавливается при расхождении; повторная сборка того же изменения сохраняет номер. Повышения minor/major сбрасывают младшие части по SemVer. Текущая настройка версионирования выпущена как **0.2.1**.

## Откуда берётся текущий трек

```text
Звук: Media Session + DOM
  → MAIN world: entrypoints/page
  → window.postMessage
  → isolated Content Script
  → Chrome runtime messaging
  → Background service worker
  → chrome.storage.local, отдельная запись для каждой вкладки
  → storage.onChanged / начальный запрос Popup
  → Zustand → React UI
```

Основной источник — `navigator.mediaSession.metadata`: title, artist, album и artwork. Чтение выполняется в **MAIN world**, где находятся данные страницы; изолированный content script не предполагает, что его Media Session совпадает с Media Session сайта. Публичные поля нормализуются и проверяются перед передачей.

В выполненной проверке на Chrome 156 metadata синтетической страницы были видны также из отдельного isolated world. Это результат конкретной версии браузера и тестовой страницы; для настоящего сайта расширение использует проверенный MAIN reader.

```ts
interface Track {
  id: string | null;
  title: string;
  artist: string;
  album: string | null;
  artwork: string | null;
  url: string | null;
}
```

Для ID используются ссылки `/track/{числовой-id}`: название сопоставляется с metadata, а исполнитель — с текстом в небольшом соседнем контейнере. Хешированные CSS-классы не используются. Первую ссылку на странице текущей композицией не считают. Несколько разных подходящих ID или отсутствие достаточного подтверждения дают `id: null` и `url: null`.

При сравнении исполнителей учитываются пробелы около запятых: отдельный DOM-элемент с запятой может дать `Alice , Bob`, тогда как Media Session сообщает `Alice, Bob`. Порядок и полный состав имён по-прежнему должны совпадать. Разбор предоставленного скрипта виджета описан в [наблюдениях по виджету](docs/zvuk-widget-findings.md).

Artwork принимается как безопасный HTTPS-адрес без учётных данных и fragment. Произвольные query по-прежнему отклоняются. Для подтверждённых image-optimizer маршрутов `cdn-new.zvuk.com/desktop-data/_next/image` и `zvuk.com/_next/image` разрешены ровно `url`, `w`, `q`: проверяются известные размеры, числовое качество и вложенный публичный HTTPS-источник подтверждённого image-CDN без query/fragment/credentials/портов. Это исправляет исчезавшие настоящие обложки Media Session; параметры не удаляются и URL не переписывается. Если подходящей обложки нет, UI показывает заглушку. Отсутствующие альбом, ID и ссылка не выдумываются. `playbackState` читается отдельно: наличие metadata само по себе не означает, что звук сейчас воспроизводится.

У Media Session нет универсального события смены metadata, поэтому MAIN reader проверяет состояние раз в **1000 ms**. Одинаковые снимки повторно не отправляются. DOM проверяется тем же циклом, поэтому смена маршрута SPA и позднее появление ссылки учитываются без наблюдателя на весь документ. Глобальные API плеера не переопределяются.

На `pagehide` останавливаются таймеры, наблюдатели и прикладные listeners; после возврата из BFCache (`pageshow.persisted`) связь создаётся заново. MAIN bridge и content script обмениваются только типизированными публичными данными с проверкой source, origin, версии, канала и схемы. Страница остаётся недоверенным источником: этот мост не является каналом передачи секретов.

## Вкладки, хранилище и Zustand

Background проверяет отправителя, верхний frame, адрес Звука и схему сообщения. Снимки хранятся в `chrome.storage.local` под ключами `player.tab.{tabId}`, диагностические отчёты — отдельно, `diagnostics.tab.{tabId}`. Записи разных вкладок не объединяются.

Перед записью background запрашивает ключ текущего документа у content script верхнего frame и сверяет его с сообщением. Обновления во время загрузки документа повторяются content script после её окончания. Это исключает возврат снимка старой страницы из запоздавшего сообщения.

Правило выбора источника:

1. Активная вкладка Звука имеет приоритет, даже если она пока не сообщила metadata.
2. Иначе выбирается вкладка с подтверждённым `playbackState: playing` и самым свежим обновлением.
3. Если таких вкладок нет, выбирается самый свежий источник; равенство разрешается по ID вкладки.

Popup подписывается на изменения storage и восстанавливает состояние при повторном открытии. Перезапуск service worker не требует восстановления общей очереди из памяти worker: актуальные сведения находятся в storage. Закрытие вкладки или уход с Звука удаляет её записи; загрузка нового документа очищает старый снимок. При запуске нового сеанса браузера удаляются записи с устаревшими ID вкладок.

После очистки при запуске браузера background запрашивает свежий снимок у существующих content scripts. Новый канал отменяет подтверждения предыдущего обмена, поэтому одинаковые metadata тоже отправляются заново.

Store реального плеера находится в `features/player`. Он хранит полученное состояние; выбранный трек, соединение и время обновления выводятся из выбранного снимка. Zustand не разделяет объект store между popup, background и content script: их связывают Chrome Messaging и Storage API.

Карточка различает отсутствие вкладки Звука, ожидание metadata, обнаруженный трек и ошибку получения данных. Воспроизведение, пауза и отсутствие подтверждённого состояния обозначаются отдельно.

Существующий `features/downloads` сохраняет свою демоочередь с действиями `addTask`, `removeTask`, `updateProgress`, `updateStatus`, `clearCompleted` и повтором ошибки. Она показывается только в предпросмотре или после подтверждения отсутствия вкладок Звука. Как только появляется любая вкладка Звука, включая вкладку без metadata, демоочередь скрывается и её таймер останавливается. При первоначальном подключении демо не мелькает вместо реальных данных. Действие скачивания и его результат не добавляются в демоочередь.

## Скачивание текущего трека

В режиме открытого Звука доступна кнопка **«Скачать песню»**. Она отправляет в background идентификатор вкладки и текущие метаданные, без произвольного URL. Background запрашивает свежий источник у MAIN reader через content script и проверяет ключ документа. Если композиция уже сменилась, скачивание не начинается.

Прямой файл определяется по одному выбранному `currentSrc` media-элемента: поддерживаются обычные HTTPS-ресурсы Звука с расширением `mp3`, `aac`, `flac`, `ogg`, `opus`, `wav`, `m4a` или `mp4`. Когда обнаружены кандидаты HLS именно текущего DOM ID, ресурс `.mp4` отдельно за целую песню не принимается: он может быть init-фрагментом. История HLS другого трека не блокирует подходящий прямой MP4 текущей композиции.

Для HLS MAIN world с `document_start` пассивно собирает до 32 уже наблюдавшихся публичных `.m3u8` с точного `cdn-hls-slicer.zvuk.com`. По подтверждённому DOM ID текущего трека выбираются адреса с совпадением по границам цифр. Сервис читает максимум восемь кандидатов и требует единственный настоящий master-плейлист; неоднозначность или отсутствие источника отображаются как причина отказа. Первый media-плейлист или последний сетевой запрос источником по умолчанию не становится.

Изначально из master выбирается AAC с наибольшим объявленным `BANDWIDTH`, а при отсутствии поддержанного AAC выбирается FLAC. Media-плейлист должен быть конечным VOD fMP4. Сервис читает init и сегменты, проверяет ISO BMFF-структуру и соответствие аудиокодека объявленному AAC/FLAC, затем собирает данные по порядку. Итоговый файл — **фрагментированный MP4 с расширением `.m4a`**. Объявленная полоса потока указывает параметры плейлиста.

Если запрос ключа начального фрагмента вернул HTTP 400 или результат `hls-wrapped-key`, загрузчик может выбрать один уже прочитанный вариант из того же master. Его init и все сегменты должны быть без шифрования, а длительность должна совпадать с исходным вариантом с допуском в одну секунду. Короткие превью, плейлисты вне master и варианты, требующие ключ, пропускаются. Если подходящего варианта нет, Popup сохраняет исходную причину.

Поддерживается обычное HLS-шифрование `AES-128` с `KEYFORMAT=identity`: 16-байтный ключ читается по URI самого плейлиста, импортируется как неэкспортируемый `CryptoKey`, исходные байты очищаются. IV берётся из тега или номера сегмента; для зашифрованного init требуется явный IV. Ключи и адреса ресурсов остаются в памяти MAIN reader и не передаются в background/storage/логи. `SAMPLE-AES`, CENC, EME/DRM-сигналы и обращения к лицензиям отклоняются.

Обычный raw identity-ключ поддержан для CDN. В найденном движке сайта специальный обработчик добавляет `X-Encrypted-Key` и преобразует ответ перед передачей Shaka. В v0.3.1 расширение генерирует этот заголовок локально только для точного same-origin keyserver URI после проверки track ID и публичных параметров. Успешный ответ отменяется до чтения тела и передаётся в Popup как `hls-wrapped-key`. Преобразование ответа сервиса ещё требует доработки. Реальный запрос в авторизованной сессии этой сборкой не проверен.

Плейлисты, init и сегменты ограничены точным HTTPS CDN, без query, fragment, credentials и портов. Ключевой URI берётся из плейлиста. Для маршрута `https://zvuk.com/keyserver/api/v1/key` допустимы ровно три публичных параметра (`track_id` с ID текущего трека, `quality=hq|lossless` и `content_type=track`). После проверки этот маршрут использует `credentials: same-origin` и генерируемый заголовок `X-Encrypted-Key`. CDN использует `credentials: omit`. Все запросы сохраняют `redirect: error` и `referrerPolicy: no-referrer`. Неизвестные и повторные параметры, подписи, другие маршруты, hosts и адреса лицензий отклоняются. Поддержанный VOD ограничен 1000 сегментов и 1800 секундами. Live, byte ranges и discontinuity пока отклоняются.

Между началами HLS-запросов выдерживается **не меньше 300 мс**, включая плейлисты, init, сегменты и identity-ключи. Очередь общая для повторных попыток внутри одной страницы. Одновременно читаются до двух ответов. Ожидание отменяется вместе с заданием. Срок подготовки ограничен 150 секундами, а 15-секундный таймаут ресурса начинается после выхода из очереди. Лимит данных на попытку — 64 МиБ суммарно, 8 МиБ на init или сегмент, 256 КиБ на плейлист и 16 ключей. Автоматических повторов нет.

В `features/downloads/services/hls-download.ts` выбирается вариант, проверяются данные и собирается M4A. `hls-resource-reader.ts` проверяет URL, запускает и отменяет запросы и считает объём прочитанных данных. Для локальной проверки в `downloadHlsTrack` можно передать свои `fetchResource` и `pacer`. Это позволяет подменять сетевые ответы в тестах с теми же проверками адресов, формата и лимитов, что в production.

Popup показывает прогресс подготовки. Content script передаёт прогресс и heartbeat раз в пять секунд только во время задания, чтобы background мог подтвердить актуальность операции. Уход со страницы, таймаут или потеря задания после перезапуска worker отменяют подготовку; действие можно повторить.

Background сохраняет одну последнюю попытку на вкладку в `download.attempt.{tabId}`: этап, процент, публичные metadata, ограниченный код ошибки и ID загрузки Chrome. Popup восстанавливает её через Chrome Messaging и `storage.onChanged`, поэтому закрытие окна не стирает причину отказа. Предыдущая композиция подписывается отдельно. После перезапуска worker незавершённая подготовка без активного задания отменяется; состояние уже запущенной загрузки уточняется у Chrome. Закрытие вкладки удаляет её запись.

Готовый Blob создаётся в контексте страницы. В background передаётся только временный `blob:https://…` адрес готового файла; затем `chrome.downloads.download` открывает диалог сохранения с безопасным именем `MusicLoader/Исполнитель - Название.m4a`. Popup различает подготовку, ожидание окна сохранения, передачу Chrome и подтверждённое Chrome завершение или прерывание. После `complete`/`interrupted`, отмены или замены канала Blob URL освобождается; запоздавший ответ отменённого задания тоже освобождается. Резервный TTL — пять минут, одновременно удерживается один готовый файл. Прямые поддержанные файлы передаются Chrome со своим расширением.

На **15%** выбран и прочитан media-плейлист. Следом идут начальный фрагмент и его ключ, если фрагмент зашифрован. Popup показывает, какой запрос не удался, и HTTP-статус, если браузер его раскрыл. В отчёте кнопки **«Копировать диагностику»** это поля `attempt.request.resource`, `kind` и `httpStatus`. Если `httpStatus: null`, статус неизвестен. После повторного открытия Popup причина остаётся видимой. Отчёт содержит публичные метаданные и ограниченные поля диагностики. Адреса ресурсов, тела ответов, заголовки и ключи в отчёт не попадают.

**Скачивание настоящей музыки в авторизованной пользовательской сессии пока не проверено автоматически.** Полученный реальный HLS-отчёт использован для реализации структуры; полный путь подготовки, AES-128 и сохранения проверен на собственном AAC-fixture в Chrome. Результаты и точные пределы подтверждения — в [наблюдениях по HLS](docs/zvuk-hls-findings.md).

## Запись звука вкладки

Когда открыт Звук, действие **«Записать звук вкладки»** доступно в разделе **«Дополнительные действия»**. Оно открывает отдельную вкладку MusicLoader, чтобы запись продолжалась после закрытия Popup. Этот режим использует системное окно выбора Chrome через `getDisplayMedia` и сохраняет выбранный звук в WebM/Opus в реальном времени.

1. Поставьте трек на паузу в начале. Откройте **«Записать звук вкладки»**.
2. Нажмите **«Начать запись»**, выберите вкладку Звука и включите передачу её звука в окне Chrome.
3. Включите трек. По окончании вернитесь в MusicLoader, нажмите **«Остановить запись»** и прослушайте результат.
4. Нажмите **«Сохранить WebM»** и выберите место сохранения в Chrome.

В файл попадает весь доступный для захвата звук выбранной вкладки. Chrome кодирует его заново в Opus. Максимальная длительность — 15 минут, готовая запись остаётся в памяти до закрытия вкладки MusicLoader или следующей успешной записи. Выбор экрана или окна отклоняется. Сохранение использует уже выданное разрешение `downloads`, а захват запускается через подтверждение пользователя в Chrome.

## Скрипт сбора данных из пользовательской сессии

Файл: [`scripts/collect-zvuk-diagnostics.js`](scripts/collect-zvuk-diagnostics.js). Скрипт работает отдельно от установленного расширения. Запускается вручную в Console страницы Звука, дополнительных разрешений Chrome не запрашивает.

1. Откройте Звук, включите музыку и откройте DevTools (`F12` → **Console**), выбрав контекст самой страницы.
2. Откройте файл скрипта как текст, скопируйте его целиком и вставьте в Console.
3. В течение 30–60 секунд переключите 2–3 композиции и дождитесь начала воспроизведения. Через 60 секунд наблюдение остановится автоматически; ранняя остановка: `musicLoaderDiagnostics.stop()`.
4. Скопируйте итоговый отчёт командой Console:

   ```js
   copy(JSON.stringify(musicLoaderDiagnostics.stop(), null, 2));
   ```

5. Пришлите полученный JSON для следующего этапа. Полный HAR, cookies, заголовки авторизации и ссылки из Network не нужны.

Доступны также `musicLoaderDiagnostics.report()` для текущего отчёта и `await musicLoaderDiagnostics.copy()` для явного копирования через Clipboard API. Если Clipboard API недоступен, используйте команду Console выше. Повторная вставка скрипта освобождает ресурсы предыдущего запуска.

Отчёт включает публичные title/artist/album, выбранные media-источники в обезличенном виде, DNS-hostname, protocol, разрешённое расширение и MIME, `hasQuery`, ограниченное количество query-параметров, признаки HLS/DASH/сегментов/blob/MediaSource и EME. Пути, полные адреса, значения параметров, fragment, cookies, токены, заголовки и тела ответов не собираются. Качество остаётся неизвестным. Скрипт наблюдает Web APIs, не выполняет запросы, не изменяет поток, не перехватывает `fetch`/XHR и ничего не скачивает.

Пределы: 60 секунд, 500 ресурсов за пакет, 10 000 ресурсов всего, 64 группы обезличенных признаков и 10 media-элементов. `pagehide` завершает наблюдение и освобождает таймер, observer и listener.

## Дополнительный HLS-инспектор

В расширенном пользовательском отчёте master объявляет HE-AAC v2, два AAC-LC-варианта и FLAC; media-плейлисты содержат VOD, 21 сегмент, init map и `AES-128 identity`. Это декларации и структура плейлистов, а не результат декодирования настоящего FLAC-потока. Подробности: [наблюдения и ограничения](docs/zvuk-hls-findings.md). Инспектор остаётся дополнительным инструментом исследования; для обычной кнопки скачивания его запуск не нужен.

Файл [`scripts/inspect-zvuk-hls.js`](scripts/inspect-zvuk-hls.js), **версия 2**, проверяет структуру плейлистов. Вставьте его в Console Звука, затем **в течение первых 15 секунд переключите один трек и дождитесь начала воспроизведения**. Страницу не перезагружайте: это остановит скрипт. Для копирования итогового отчёта выполните:

```js
copy(JSON.stringify(await musicLoaderHlsReport.done, null, 2));
```

Инспектор использует снимок истории и `PerformanceObserver`, который 15 секунд ловит новые запросы. При пустой истории он продолжает ждать; если observer недоступен, включается ограниченная периодическая проверка истории. В отчёте `version: 2`, раздел `discovery` со счётчиками наблюдений/причин исключения и для каждого плейлиста источник наблюдения и metadata на этот момент. Смена композиции во время захвата не означает автоматической привязки плейлиста к треку.

Читаются только наблюдавшиеся `.m3u8` с точного `https://cdn-hls-slicer.zvuk.com`, максимум восемь уникальных плейлистов за запуск. Повторные наблюдения, включая собственные запросы инспектора, не создают повторных чтений. Запросы без cookies и служебных заголовков; перенаправления не разрешены. URL с query, fragment, credentials или портом пропускаются, а причина исключения отражается только счётчиком. Нет запросов сегментов, init-фрагментов, ключей и лицензий. CORS не обходится: при недоступном плейлисте в отчёте будет безопасный статус ошибки.

Вместо содержимого плейлистов выводятся только тип, число и длительность сегментов, признаки init map/byte range/discontinuity, известные методы шифрования и объявленные CODECS/BANDWIDTH. URI и произвольные строки не выводятся. Объявленная полоса пропускания не является измеренным битрейтом аудио. Отсутствие KEY-тегов не доказывает отсутствие DRM; инспектор не выбирает текущую песню по первому или последнему запросу.

Пределы инспектора: 128 KiB и пять секунд на плейлист после начала запроса, два одновременных запроса с интервалом между началами **не меньше 300 мс**, общий срок 30 секунд. Автоматических повторов нет. По окончании 15-секундного окна завершаются уже начатые чтения. `musicLoaderHlsReport.stop()`, уход со страницы или повторная вставка отменяют незавершённые запросы и освобождают observer/таймеры. API `report()` возвращает текущий обезличенный отчёт, `done` — итоговый; сразу после запуска `done` ожидает завершения захвата. Даже при `candidateCount: 0` раздел `discovery` помогает определить, что наблюдалось и какие фильтры сработали.

## Безопасная диагностика аудио

Диагностику включают вручную для выбранной вкладки в popup. Она использует доступные Web APIs страницы и не требует `webRequest`, доступа ко всем сайтам или чтения заголовков запросов.

| Наблюдение | Что можно сказать |
| --- | --- |
| Суффиксы MP3/AAC/FLAC/OGG/OPUS/WAV/MP4 | Признак формата/контейнера по имени ресурса, без проверки байтов |
| `PerformanceResourceTiming.contentType`, если браузер его раскрывает | Наблюдаемый MIME; доступность и детализация ограничены браузером и сервером |
| `source.type` для реально выбранного media source | Объявленный страницей MIME, а не проверка ответа сервера |
| `.m3u8`, `.mpd`, `.m4s`, MIME MPEG-TS | Признаки HLS, DASH или сегментов |
| `currentSrc` начинается с `blob:` | Используется blob-источник; это само по себе не доказывает MSE |
| `mediaKeys` / событие `encrypted` | Признаки EME/зашифрованных данных; конкретная DRM-система не определяется |
| Качество, битрейт, lossless | Не установлены; `quality` остаётся `null` |

Отчёт содержит только ограниченные списки признаков, MIME из whitelist, счётчик и булевы флаги. Полные и подписанные URL, пути, query, cookies, Authorization, пароли и содержимое ответов не сохраняются и не выводятся. MIME-параметры отбрасываются. Перехвата/подмены `fetch`, XHR или media API, чтения аудиопотока, запросов лицензий, декодирования и дешифрования нет.

Наблюдатель ресурсов обрабатывает не более 500 записей за пакет, счётчик ограничен 10 000; listeners media-элементов — не более 10. Выключение диагностики освобождает observer и listeners. События, произошедшие до включения, могут быть недоступны. Отсутствие признака DRM не доказывает отсутствие DRM.

`audio/mp4` сам по себе подтверждает только контейнер. В расширенном реальном отчёте кодеки объявлены в master, а качество декодированного аудио остаётся неизвестным. Диагностика и инспектор не выполняют подготовку файла и не запрашивают ключи; HLS downloader делает это отдельно только по нажатию пользователя.

## Архитектура, компоненты и сборка

```text
src/
├── app/                  # React popup и его HTML
├── components/ui/        # Оригинальные shadcn/ui-примитивы
├── components/<Block>/   # Составной TSX + SCSS + index.ts
├── features/player/      # Track normalization, DOM identity, выбор источника, store/hooks
├── features/diagnostics/ # Безопасные признаки ресурсов и проверка отчётов
├── features/downloads/   # Прямой файл, поиск и сборка HLS, демоочередь
├── features/recording/   # Запись аудио выбранной вкладки в WebM
├── entrypoints/
│   ├── page/             # MAIN world: Media Session и Web APIs
│   ├── content/          # ISOLATED world: валидируемый мост к runtime
│   └── background/       # MV3 service worker и storage
├── shared/               # Общие типы, сообщения и cn()
└── styles/globals.css    # Tailwind, база и токены единой тёмной темы
```

Rsbuild собирает страницы `popup.html` и `recorder.html` и три самостоятельных служебных скрипта с фиксированными именами `page/page.js`, `content/content.js`, `background/background.js`. Страницы могут совместно использовать чанки React. В production код минифицируется, а development-сборка дополнительно генерирует source maps. Manifest указывает на локальные файлы.

Manifest запрашивает `storage`, `downloads` и `host_permissions: ["https://*.zvuk.com/*"]`; этот шаблон включает корневой домен. Разрешение `downloads` нужно для пользовательского сохранения файла через браузер. Оба page/content script объявлены статически с нужным world. Разрешения `tabs`, `cookies`, `webRequest` и `<all_urls>` не требуются. Хранилище ограничено доверенными контекстами расширения; content script пишет через background.

Стандартный UI-примитив добавляют командой `npx shadcn@latest add <name>`. CLI использует `components.json` и размещает исходники в `src/components/ui/`. Button, Card, Badge, Progress, Tabs, Dialog и Tooltip установлены оригинальным CLI; локальные адаптации — общий импорт `cn`, перевод закрытия и передача значения в доступный Progress Root. При добавлении проверьте импорт `cn`: CLI может использовать одноимённый npm-пакет напрямую.

Для собственного визуального компонента создайте `CurrentTrack/CurrentTrack.tsx`, `CurrentTrack.scss` и `index.ts`. Один самостоятельный БЭМ-блок соответствует одному React-компоненту: `current-track`, `current-track__title`, `current-track--empty`. Специфичные стили находятся рядом, без Tailwind utility-классов в составном JSX. SCSS не вмешивается во внутренние элементы другого БЭМ-блока; вложенные имена `block__body__title` не используются. Примитивы shadcn/ui сохраняют Tailwind-стили.

Глобальный Tailwind CSS обрабатывается отдельно от Sass. Компоненты используют CSS-переменные темы. Размер документа popup задан через `html[data-surface="popup"]`, `--popup-width` и `--popup-height`. Целевой размер окна — 420 × 560 CSS-пикселей, высоту Chrome ограничивает доступным местом. Карточка, очередь и диагностика прокручиваются в одной области, а состояние связи остаётся внизу. В обычной вкладке режим `preview` подстраивается под ширину и высоту окна.

## Проверки и ограничения

Запускайте `typecheck`, `test` и `build` командами выше. Логика нормализации, сопоставления DOM и редактирования диагностических отчётов проверяется отдельно от UI. Браузерный сценарий использует настоящий extension-контекст и синтетическую Media Session на локальной странице-заглушке:

```sh
npx playwright install chromium
npm run test:browser
```

Для установленного актуального Google Chrome в PowerShell:

```powershell
$env:MUSICLOADER_BROWSER_CHANNEL = 'chrome'
npm run test:browser
```

Сценарий предназначен для проверки разделения MAIN/isolated world, смены metadata без перезагрузки, SPA, восстановления popup, выбора вкладки, перезапуска worker, очистки после закрытия вкладки, пустых и ошибочных состояний. Настоящее окно действия открывается без эмуляции viewport. Результаты выполнения смотрите в выводе команд; снимки сохраняются в `artifacts/`.

Для v0.3.1 прошли TypeScript, 209 автоматических тестов, production-сборка и проверка Manifest. В Chrome 157.0.8103.79 на локальных тестовых данных проверены заголовок `X-Encrypted-Key`, отдельное состояние `hls-wrapped-key`, выбор открытого варианта, сохранение M4A и запись звука вкладки в WebM/Opus. Сохранённые файлы сравнены с данными теста, а запись WebM декодирована с проверкой наличия звука. Запросы к настоящему серверу ключей в авторизованной сессии этой проверкой не выполнялись.

Для v0.2.5 прошли TypeScript, **207 автоматических тестов в 32 наборах**, production-сборка и проверка Manifest. Chrome **157.0.8103.50** на тестовой странице подтвердил отдельные сообщения об отказах init (HTTP 503) и ключа (HTTP 403), восстановление ошибки после открытия Popup и обезличенный отчёт. Проверено, что браузер отправляет тестовую cookie ключевому серверу своего origin, а CDN её не получает. После успешных ответов Chrome сохранил побайтово проверенный M4A и воспроизвёл его до конца.

Сценарий Chrome также проверяет ширину настоящего Popup 420 px, передачу MAIN → storage → React, смену трека при SPA-навигации, отсутствие дублей, неоднозначный ID, несколько вкладок и восстановление metadata после остановки worker. Демоочередь скрывается при открытом Звуке. Повышения patch/minor/major проверены через npm hooks в изолированных временных проектах. Проверка согласованности сохраняет текущие версии, а расхождение блокирует повышение до записи файлов.

Для v0.2.4 проверена обложка подтверждённой формы image-optimizer с вложенным публичным URL: MAIN → Chrome storage → Popup, загрузка собственного SVG и восстановление после повторного открытия Popup. Unit-тесты проверяют допустимые размеры/hosts и отклонение вложенных приватных URL, лишних параметров и подмены адресов. Полный тест скачивания по-прежнему использует собственный **raw-key** fixture и не подтверждает поддержку специального преобразования ответа ключевого сервера сайта.

Для v0.2.3 собственный AES-128 AAC-fixture использует форму `/drm/track/t60001-fixture/` и точный same-origin маршрут identity-ключа с тремя публичными параметрами. Chrome подтвердил отсутствие cookies и Authorization в запросе ключа при установленной тестовой cookie, один запрос ключа на задание, сохранение M4A с побайтовым совпадением и воспроизведение до `ended`. Unit-тесты блокируют неправильный track_id до чтения аудио/ключа, неизвестные и авторизационные параметры, SAMPLE-AES, проверяют отказ 403 без повтора и очистку байтов при отмене. Реальные аудио и ключи пользователя в тестах не используются.

Для v0.2.2 дополнительно проверены HLS-discovery и копирование полного обезличенного отчёта через MAIN → background → storage → Popup, распознавание исключённого плейлиста с query без повторного запроса этого адреса и успешная подготовка/сохранение собственного HLS после удаления всех audio/video из тестового DOM. Большие пакеты с master перед 1000 обычными ресурсами покрыты unit-тестами; причина исходного пользовательского `no-source` этим не установлена.

В сборке v0.2.0 проверены интервалы запросов и отмена очереди, DOM с отдельными элементами имён и запятых, сохранение причины отказа после повторного открытия popup, отмена нативного сохранения Chrome и копирование отчёта без сетевых URL. При отсутствии работающего content script сохранённые metadata не выдаются за подключённый источник.

Полный HLS-путь проверен на собственном AAC-fixture: init и сегменты зашифрованы тестовым AES-128 identity, расширение подготовило M4A, настоящий Chrome Downloads API сохранил файл, а его байты совпали с исходным fixture размером около 13 KB. Chrome воспроизвёл собранный M4A до события `ended`. Unit-тесты также проверяют порядок сегментов, выбор AAC, структурную проверку FLAC, кеш/очистку ключей, отмену, пределы размера и блокировку неподдерживаемого DRM. Это не скачивание песни с настоящего сервиса.

Дополнительный сценарий Chrome подтвердил отмену активной HLS-подготовки после принудительной остановки worker и успешное сохранение при повторном нажатии.

Мост прямого скачивания отдельно проверен с синтетическим `currentSrc`: сверены источник, безопасное имя и `saveAs`, блокировки подписанного URL/EME и отсутствие ресурсного URL в storage. Console-скрипты покрыты тестами редактирования URL, discovery, пределов, отсутствия посторонних запросов и очистки ресурсов.

Также проверены уход с домена и очистка storage, повторный запрос неизменившихся metadata после очистки и остановка/возобновление listeners и таймеров через искусственные события `pagehide` / `pageshow.persisted`. Возврат настоящего сайта из BFCache этим сценарием не подтверждён.

HLS-инспектор отдельно проверен в Chrome на собственном тестовом плейлисте: обнаружение через Performance API, `credentials: omit`, отсутствие cookie даже при её наличии в тестовом профиле, отсутствие запросов init/сегментов/ключей и полных URL в итоговом JSON. Проверены master/media-плейлисты, методы шифрования, пределы чтения и отмена запросов.

Регрессия пользовательского `candidateCount: 0` проверена в версии 2: при пустой истории инспектор остаётся активным, принимает плейлист через последующий Resource PerformanceObserver и завершает `.done` после окна захвата. В Chrome подтверждены `observedVia: observer`, одно чтение нового плейлиста и отсутствие повторных запросов от собственного наблюдения. Очистка истории используется только в тестовом fixture для воспроизведения случая; сам скрипт не меняет браузерный буфер.

**Автоматизированная проверка скачивания в авторизованной пользовательской сессии Звука не выполнялась.** Пользователь передал обезличенный HLS-отчёт с объявленными кодеками, VOD-сегментами и AES-128 identity. Реальная доступность ресурсов, качество декодированного аудио и сохранение настоящей песни требуют ручной проверки; синтетический Chrome-fixture эти свойства сервиса не подтверждает.

Ручная проверка после установки:

1. Обновите расширение и вкладку Звука, запустите композицию, сверьте title/artist/album и обложку с плеером.
2. Переключите несколько композиций и выполните SPA-переход: карточка должна обновляться; неоднозначный ID остаётся пустым.
3. Поставьте воспроизведение на паузу: карточка не должна утверждать, что трек играет только по наличию metadata.
4. Закройте и снова откройте popup, затем откройте вторую вкладку Звука и проверьте правило выбора источника.
5. Закройте вкладку/уйдите с сайта: прежние сведения не должны выдаваться за текущий трек этой вкладки.
6. Включите и выключите диагностику; проверьте обезличенные признаки и отсутствие секретов в отчёте. Пустые признаки не заменяются догадками.
7. После обновления расширения обязательно перезагрузите Звук, чтобы source tracker видел запросы с начала документа. Сверьте номер в заголовке Popup с текущим `package.json`, проверьте отсутствие демоочереди и определение текущего ID. Нажмите «Скачать песню», дождитесь подготовки и диалога Chrome. При отказе закройте и снова откройте popup: причина должна сохраниться. Включите аудиодиагностику, нажмите «Копировать диагностику» и проверьте код, версию, `hlsDiscovery` и отсутствие служебных адресов. Сохранённый HLS-файл должен иметь расширение `.m4a` и воспроизводиться целиком. Console-отчёт нужен только при исследовании неподдержанного случая.

Предыдущая проверка `npm audit` обнаружила два связанных предупреждения низкой важности в dev-цепочке `@rsbuild/plugin-sass` → `deepmerge`. Предлагаемое автоматическое исправление понижает Sass-плагин несовместимым образом и не применяется; эта цепочка не включается в runtime расширения.
