# Разбор сохранённой сборки Звука — 30.10.2026, v0.2.4

## Вывод для прямого скачивания в Chrome

В сохранённой сборке подтверждён путь веб-воспроизведения через выбор источника и Shaka. В просмотренных модулях отдельная операция выдачи готового файла не обнаружена. Это согласуется с [официальной справкой Звука](https://help.zvuk.com/article/48281), где офлайн-загрузка указана только для мобильного приложения. Попытка повторно получить актуальный клиентский бандл из публичной страницы вернула скрипты браузерной проверки, поэтому актуальная сборка плеера и конкретный авторизованный трек отдельно не проверены.

Практический путь для MusicLoader уже есть в `downloadHlsTrack`. Когда основной вариант возвращает `hls-wrapped-key`, загрузчик читает объявленные в том же master открытые варианты и проверяет длительность. При наличии полного открытого варианта он собирает файл без перекодирования. Отдельный запрос `.m3u8` может отсутствовать у встроенного master, поэтому `hls-no-source` и `hls-wrapped-key` важно различать. В Chrome это можно проверить для конкретного трека через отчёт **«Дополнительные действия → Копировать диагностику»** после нажатия **«Скачать песню»**. Если диагностика аудио включена, в отчёте также будут счётчики наблюдавшихся плейлистов без адресов и параметров доступа.

## Сохранённая сборка

В `zvuk` сохранён экспорт клиентских ресурсов Next.js v8.20.1, включая 81 JS-файл основного каталога chunks (около 5,9 МБ). Это собранный клиент, а не исходный TypeScript-проект; source maps не найдены. Анализ выполнен статически, без запуска кода сайта, запросов к его API, чтения значений cookies/токенов или декодирования статической криптографической конфигурации. Исходный экспорт в сборку расширения не включается.

## Получение и выбор аудио

`mediaContents` получает `ids`, `quality`, `encodeType` и `useHLSv2`. Клиент объединяет `stream` и `streamV3.hls`, обновляет истёкший `expire`. Для Track порядок кандидатов — `hls → flacdrm → high → mid`, для неавторизованной ветки используется `preview`; HLSv2 пропускает `flacdrm`.

API-quality `hifi`/`hq` и encodeType `fp`/`wv` относятся к GraphQL. Они не доказывают допустимость `quality=hifi` в keyserver URI: значения параметров ключа задаются серверным плейлистом. Текущая узкая allowlist ключевого маршрута на основании этого кода не расширяется.

`masterPlaylist.data` может загружаться как `data:application/x-mpegURL`. Тогда сетевого master `.m3u8` вообще может не быть. Это подтверждённая ветка кода, но её активность в конкретной пользовательской сессии не установлена. Наблюдение Resource Timing не покрывает встроенный master автоматически.

Движок создаёт `new Audio` без помещения элемента в DOM; при поддержке использует `AudioContext.createMediaElementSource`. Поэтому пустой результат `querySelectorAll('audio,video')` не противоречит воспроизведению. Расширение сохраняет независимое чтение Media Session и пассивный поиск HLS.

## Существенное уточнение о ключах

При truthy `encryptedKey` в обёртке подключается специальный обработчик. Для key request type 6 он устанавливает `X-Encrypted-Key`, а для response type 6 преобразует данные перед передачей Shaka. В этой ветке нет проверки «ответ уже является raw AES-key» по длине или response header. Значения конфигурации и заголовка здесь не приводятся; алгоритм обработки не воспроизводился. Другой обработчик включает `allowCrossSiteCredentials` для этого типа запросов.

Повторная безопасная проверка ранее предоставленного HAR подтвердила только **наличие** `X-Encrypted-Key` в запросе, без чтения его значения. Это меняет прежний вывод: HTTP 200 и 16 байт в HAR недостаточно для признания ответа готовым AES-128 identity-ключом. Ветка ответа endpoint без этого заголовка из frontend не доказывается ни рабочей, ни нерабочей.

Origin rewrite заменяет только префикс `https://zvuk.com/keyserver/` на `window.location.origin + '/keyserver/'`; query сохраняется. Копирование заголовка, перенос токенов, восстановление статической конфигурации и специального протокола в расширении не реализованы. Поддержка обычного raw identity-ключа в downloader не подтверждает поддержку этой ветки сервиса. Собственный AAC-fixture проверяет только raw-key сценарий.

## Метаданные и обложки

Media Session получает `currentItem.title`, имена артистов через `join(', ')`, название релиза и artwork. `playing`/`paused` устанавливается отдельно. В рассмотренном эффекте возврат при отсутствии `currentItem` не очищает metadata; нового надёжного сигнала завершения композиции из этого не следует.

Mini-player использует ссылку элемента и `title` названия, полный список артистов находится рядом. Сопоставление `/track/{id}` с metadata и проверкой однозначности сохраняется. `data-testid` зависит от route/section и `TestingProvider.isShow`, поэтому не является обязательным production-атрибутом.

Обложки действительно создаются в форме `https://cdn-new.zvuk.com/desktop-data/_next/image?url=…&w=…&q=75`. Запрошенные размеры 200/380/600 преобразуются в 280/420/700. Это обнаружило ошибку расширения: запрет любого query отбрасывал реальные публичные обложки.

В v0.2.4 добавлено узкое разрешение известных optimizer routes с единственными `url`, `w`, `q`. Проверяются размер, качество и вложенный HTTPS-адрес подтверждённого image-CDN без query, fragment, credentials и портов. Исходный URL не переписывается. Лишние/авторизационные параметры, другой host и вложенные proxy URL отклоняются. Секретные URL не превращаются в «публичные» удалением параметров.

## Что это означает для проекта

Исправление папки `/drm/` остаётся обоснованным: имя пути не определяет метод HLS. Однако полноценное сохранение настоящего потока не подтверждено, пока не проверены профиль получения ключей и источник master. Обложки и metadata можно исправить независимо; специальная обработка ответов ключевого сервера остаётся ограничением. Эти выводы заменяют предположение о готовом raw-ключе на основании одной длины ответа.

Для v0.2.4 прошли TypeScript, 195 автоматических тестов, production-сборка и Manifest. Chrome 156 подтвердил передачу и отображение собственной обложки через optimizer URL, её восстановление после повторного открытия Popup и существующие сценарии на тестовом raw-key AAC. Сайт в браузерной проверке заменён синтетической страницей; авторизованная сессия Звука не проверялась.

Отчёт v0.2.4 с тремя совпавшими плейлистами, `hls-request-failed` и прогрессом 15% подтверждает, что media-плейлист прочитан. Этот код не различал сбой чтения init и ключа. С v0.2.5 `attempt.request` сохраняет вид ресурса, тип сбоя и доступный браузеру HTTP-статус. Для точного same-origin keyserver URI разрешена обычная браузерная сессия. Доступность ключа без специального заголовка в реальной сессии всё ещё требует проверки.

В отчёте v0.2.6 запрос ключа начального фрагмента для трека «Сердце на костре» вернул HTTP 400. В предыдущем HAR для другой композиции запрос веб-плеера с дополнительным служебным заголовком вернул 200, а оба записанных media-плейлиста объявляли AES-128. Эти наблюдения согласуются с особой обработкой ключей, но тело ответа 400 и параметры текущей сессии не исследованы. По этому отчёту нельзя определить, есть ли у «Сердца на костре» доступный незашифрованный вариант.

Скриншот сервера от 12.11.2026 уточнил причину HTTP 400 сообщением `Param encrypted_key is required`. Статическая проверка показала, что заголовок `X-Encrypted-Key` заполняется случайной восьмизначной строкой из букв и цифр. Перед обработкой ответа плеер использует это значение совместно со своей конфигурацией. В v0.3.1 добавлена генерация заголовка только для проверенного маршрута ключа. Ответ HTTP 2xx отмечается кодом `hls-wrapped-key` и закрывается до чтения тела. Дальнейшее преобразование ответа требует отдельной реализации и проверки.
