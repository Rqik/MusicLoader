# Правила работы с MusicLoader

## Роли и очередь

- Координатор ведёт [очередь задач](docs/TASKS.md), согласует передачу макета в разработку, сверяет результат с критериями приёмки и оформляет проверенные изменения отдельными Conventional Commits.
- Дизайнер проходит основные сценарии в текущем интерфейсе, фиксирует UX-аудит и готовит интерактивный макет. Макет показывает начальное состояние, основное действие, раскрытие дополнительных действий, ошибки и восстановление. Перед реализацией дизайнер передаёт разработчику ссылку на макет и согласованное поведение.
- Разработчик реализует согласованное поведение через обычные точки входа расширения, сохраняет стек и данные, покрывает критические сценарии тестами и записывает результаты проверок в очередь.

В `docs/TASKS.md` у каждой задачи указывай ответственного, статус и проверяемые критерии приёмки. Обновляй очередь при передаче работы и после проверки. Для открытых проблем записывай конкретный результат, которого пока не удалось достичь.

## Интерфейс и приёмка

- Используй [Google Modern Web Guidance](https://github.com/GoogleChrome/modern-web-guidance) для семантики HTML, адаптивности и доступности. Применяй [unslop](https://github.com/heydamir/unslop) при аудите визуальной иерархии, текста, типографики и отступов.
- Показывай обязательные поля сразу, дополнительные раскрывай по запросу. У каждого состояния должно быть одно визуально главное действие. Сообщение об ошибке должно объяснять причину и показывать следующий доступный шаг. Сохраняй введённые данные и полученный результат при ошибке или отмене операции.
- Сохраняй React, TypeScript, Rsbuild, Zustand, shadcn/ui, Tailwind CSS и Lucide. Для прикладных компонентов используй БЭМ и размещай `.module.scss` рядом с компонентом. Общие цвета, интервалы и состояния фокуса задавай токенами, повторяющиеся элементы переиспользуй.
- Проверяй изменённые экраны на ширинах 320, 390 и 1440 px, включая длинный текст, видимость действий и отсутствие горизонтальной прокрутки. Проверяй порядок и видимость фокуса, активацию с клавиатуры, ошибку и повтор, восстановление сохранённых данных. Критические сценарии закрепляй автоматическими тестами.
- Перед завершением выполни `npm run version:check`, `npm run typecheck`, `npm test`, `npm run build` и для изменений интерфейса `npm run test:browser`. Фиксируй проверенные логические изменения отдельными коммитами в формате `type(scope): summary`.

## Версии — обязательное правило пользователя

После каждого завершённого логического изменения повышай версию перед итоговой production-сборкой и сообщай новую версию пользователю. Одно изменение может включать несколько файлов и промежуточных исправлений. Повторные проверки и пересборки того же изменения не повышают версию снова.

- Исправление, небольшая правка UI, конфигурации или документации: `npm run version:patch` — `0.2.0 → 0.2.1`.
- Новая функциональность: `npm run version:minor` — `0.2.1 → 0.3.0` (patch сбрасывается).
- Несовместимое крупное изменение или явно запрошенный major: `npm run version:major` — `0.3.1 → 1.0.0` (minor и patch сбрасываются).
- Если категория не указана и это небольшая правка, используй patch без дополнительного подтверждения.

Единый источник версии — `package.json`. Команды согласуют `package-lock.json` и `public/manifest.json`; Popup и предпросмотр читают ту же версию. Не прописывай номер версии вручную в исходниках или тестах. Проверка: `npm run version:check`. Итог: `npm run typecheck`, подходящие тесты и `npm run build`; новую сборку помещают в `dist`.

Команды повышения версии не создают git-коммитов и тегов и ничего не публикуют. Не добавляй автоматическое повышение на каждый запуск сборки: оно должно происходить один раз на завершённое изменение.
